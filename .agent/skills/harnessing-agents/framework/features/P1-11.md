# P1-11. Socratic Questioning

> **Chain:** [EP-14](../principles/EP-14.md) → Clarity before commitment

## L2: Targeted Enhancement

Zero ambiguous inputs reaching the execution phase.

## L3: Design Decisions

Protocol for clarifying intent and clarifying requirements; recursive inquiry before execution; machine-readable inquiry trace-recursive records; Machine-Readability First.

## L4: Concrete Actions & Tools

- **Action:** When encountering an unclear or ambiguous input, pause execution and apply a structured Socratic interrogation pass before proceeding.
- **Action:** Probe the input using all six question categories: Clarification, Probing Assumptions, Probing Reason & Evidence, Questioning Viewpoints, Probing Implications, and Questions about the Question.
- **Action:** Record extracted clarifications as structured entries in the Requirements Ledger (P1-10) or as Context Anchors (P1-8) before proceeding to planning.
- **Tool:** Structured interrogation templates covering the 6 Socratic question types, injected into agent context at task intake.
- **Tool:** Ambiguity scoring heuristics — rate input clarity before and after the Socratic round; do not proceed if clarity score remains below threshold.

## L4: Prevention

- **`P1-11` Prevent Premature Execution:** You must prevent agents from starting implementation on ambiguous requirements. Mandate a "Socratic pause" where the agent must ask clarifying questions until the objective is clear.
- **`P1-11` Prevent Narrative Inquiry Logs:** Clarification requests and responses must follow `.harness/inquiry-response.schema.json` to enable automated intent-validation and documentation.

## L5: Gap Signals

- Agent starts coding immediately from unclear or ambiguous input without surfacing assumptions
- Requirements contain multiple valid interpretations and only one is silently chosen by the agent
- Post-execution rework reveals "I assumed you meant…" situations
- Agent builds the wrong feature due to ambiguous requirements
- No record of clarifications made during the development loop
- Reasoning tokens are wasted on implementing incorrect assumptions
- Human role is limited to reactive troubleshooting instead of proactive design
