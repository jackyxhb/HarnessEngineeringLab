# P1-9. Branch-Based Cognitive Memory

> **Chain:** [EP-2](../principles/EP-02.md) → State must outlive the session

## L2: Targeted Enhancement

Complex objectives decompose into checkpointed sub-tasks with cognitive history that survives context resets and enables parallel execution.

## L3: Design Decisions

### Branching Strategy

**Git Worktrees for Isolated Execution:** Each sub-task executes in a dedicated Git worktree (not just branch checkout), allowing multiple sub-tasks to be worked on in parallel without context switching or workspace collisions. Worktrees maintain independent working directories, index files, and HEAD pointers while sharing a single `.git` directory.

**Branch Naming Convention (Deterministic & Parseable):**
- Format: `task/{task_id}/{checkpoint_n}` or `subtask/{parent_id}/{feature}`
- Pattern: `[a-z]+-[a-z0-9]+-[a-z0-9-]*` (alphanumeric, hyphens, no underscores)
- Examples:
  - `task/p1-09/checkpoint-1` (top-level task, first checkpoint)
  - `task/p1-09/checkpoint-2-validation` (second checkpoint, descriptive)
  - `subtask/p1-09-design/schema-checkpoint` (sub-task of larger feature)
- Automation: Branch-name sensor (pre-commit hook or CI gate) rejects non-compliant names before commit, ensuring all branches are machine-addressable and resumable.

### Context Checkpointing Mechanism

**Copy-on-Write Semantics:** At each branch point (task creation, subtask spawn, or context reset recovery), capture a checkpoint snapshot containing:
1. Full prior-state hash (SHA-256 of all prior findings and task context)
2. Token count of prior execution context (for budget tracking)
3. Completion status of prior phase
4. Upstream evidence links (references to parent task and prior checkpoints)

**Checkpoint Storage Location:** `.harness/branch-checkpoints.json` (append-only JSONL-format registry) or per-branch metadata in `.harness/branch-{branch_id}-checkpoint.json`.

**Checkpoint Verification Before Branch Creation:** Before creating a new branch, the cognitive-branch workflow must:
1. Compute hash of all prior findings and accumulated context
2. Verify checkpoint file exists and matches hash
3. Verify token count does not exceed session budget
4. Only then create worktree and new tracking branch

If verification fails, escalate to human with diagnostic showing hash mismatch, missing context, or budget exhaustion.

### Parallel Execution Scope: SAS vs MAS

**SAS (Single-Agent Sequential):** Within a single agent's context window, multiple sub-task branches are *created* but *executed sequentially*. Each sub-task:
1. Creates a worktree and tracking branch
2. Executes to completion with full context
3. Commits evidence and merges to parent
4. Cleans up worktree
5. Moves to next sub-task

Sequential execution preserves full context inheritance and enables context reset recovery because evidence chains are immutable.

**MAS (Multi-Agent Parallel):** When P0-5 Orchestration Logic is mounted, the orchestrator may dispatch sub-tasks to distinct agent identities in parallel:
1. Orchestrator reads task plan from parent branch
2. Creates sub-task worktrees and branches (one per sub-task)
3. Routes each sub-task to an available agent pool member
4. Each agent executes independently on its assigned branch
5. All agents commit evidence to their respective branches
6. Orchestrator collects completed branches and initiates parallel merge-back
7. Orchestrator resolves merge conflicts (if any) using evidence-chain priority
8. Orchestrator seals merged state to parent task branch

**Transition Path:** SAS implementation requires only Git worktrees and cognitive-branch workflow (already present). MAS requires P0-5 Orchestration Logic to add supervisor routing, agent pool management, and conflict resolution. The checkpointing and evidence format remain identical; only the dispatcher and merge orchestrator change.

### Commit Message Structure (Approval of Evidence)

All commits on cognitive-branch tracking branches must include structured evidence in the commit body:

```json
{
  "evidence": {
    "what": "Specific, atomic change(s) made",
    "why": "How this resolves the sub-task requirement",
    "confirmation": "Verification method (test, lint pass, manual review, coverage metric, etc.)"
  }
}
```

This JSON structure is machine-parseable and enables automated task-resumption decisions: downstream agents or context-reset recovery can read the evidence hash and determine whether the prior phase fully completed or requires restart.

**Machine-Readability First:** All evidence records must be JSON-compatible, enabling automated auditing of completion status, blocker detection, and task-resumption routing.

## Scope: SAS vs MAS

**SAS Scope:** In single-agent mode, this feature enables a single agent to decompose complex objectives into isolated tracking branches and execute them sequentially with checkpointed progress. Each sub-task branch preserves cognitive history through structured commit messages, allowing the agent to resume work after context resets and verify completion through branch merging into the parent task.

**MAS Scope:** In multi-agent mode, this feature enables the orchestrator to dispatch sub-tasks to agent-specific branches in parallel, with each agent executing independently on its own branch. The independent commit histories form separate evidence chains that merge back into a parent task branch, enabling collective completion tracking and parallel execution without blocking.

**Transition Path:** Move from SAS sequential execution to MAS parallel dispatch by implementing P0-5 Orchestration Logic to route sub-tasks to distinct agent identities, each working on agent-specific branches. The consolidation workflow remains identical: all sub-task branches merge into the parent task branch regardless of execution parallelism.

## L4: Concrete Actions & Tools

### Branch Creation & Context Preservation

- **Action:** Invoke `/cognitive-branch` workflow to spawn sub-task worktrees and branches for complex objectives.
  - **Worktree Creation:** Use `git worktree add .claude/worktrees/{task_id}-{checkpoint_n} {parent_branch}` to create isolated execution context without switching main workspace.
  - **Branch Naming:** Create branch with deterministic name following `task/{task_id}/checkpoint-{n}` pattern; branch-name sensor rejects non-compliant names at first commit.
  - **Acceptance Criteria:** Worktree directory exists, `.git/worktrees/` registry is updated, branch is checked out and ready for work.

- **Action:** Before branch creation, verify checkpoint can be created (context is capturable and hash-verifiable).
  - **Context Capture Mechanism (Copy-on-Write):** At branch-creation time, compute SHA-256 hash of all prior-execution findings (commit message evidence, prior test results, context anchors, planning notes). Store hash and metadata in `.harness/branch-{branch_id}-checkpoint.json`.
  - **Checkpoint Schema (JSON):**

    ```json
    {
      "branch_id": "task/p1-09/checkpoint-1",
      "task_id": "p1-09",
      "checkpoint_number": 1,
      "parent_branch": "main",
      "created_timestamp": "2026-04-16T14:23:45Z",
      "context_hash": "sha256:abc123def456...",
      "prior_findings_tokens": 1850,
      "token_budget_remaining": 3150,
      "completion_status": "in-progress",
      "upstream_evidence_links": ["task/p1-09/checkpoint-0"],
      "verification_passed": true,
      "verified_at": "2026-04-16T14:23:42Z"
    }
    ```

  - **Hash Verification:** Before allowing branch creation, validate `context_hash` matches recomputed hash from prior commits, evidence records, and planning notes. If hash mismatch, escalate with diagnostic showing what changed unexpectedly.
  - **Token Validation:** Verify `prior_findings_tokens + (current_session_tokens_used)` does not exceed remaining budget. If exceeded, escalate to user for context compaction or session boundary.

- **Action:** Preserve complete prior-state context during branch switch.
  - **Delta Encoding Alternative:** If full context snapshot is too large, encode only deltas from parent branch using commit-message evidence hashes. Store parent hash in checkpoint; during recovery, recompute full state by replaying parent evidence chain.
  - **Acceptance Criteria:** Recovery from context reset can reconstruct full prior state from checkpoints + parent evidence chains without manual intervention.

### Evidence Commit & Completion Verification

- **Action:** Generate structured "approval of evidence" commits explaining *what* was done, *why* it resolves the sub-task, and *how* correctness was confirmed.
  - **Evidence Format:** Commit body must contain JSON block matching schema:

    ```json
    {
      "evidence": {
        "what": "Specific change(s): e.g., 'Enhanced L3 section with branching strategy, checkpoint schema, and SAS vs MAS scope'",
        "why": "Addresses sub-task requirement: e.g., 'L3 was aspirational; this adds deterministic branch naming, copy-on-write checkpointing, and explicit SAS vs MAS transition path'",
        "confirmation": "Verification method: e.g., 'Ran npm run smoke; he-lint.js passed all feature-ID and pillar-label checks'"
      }
    }
    ```

  - **Machine-Parseable:** All evidence records must be valid JSON; downstream tools (task-resumption logic, context-reset recovery, MAS orchestrators) parse and validate evidence structure.
  - **Acceptance Criteria:** Commit passes `npm run check` (markdownlint, cspell, he-lint); evidence JSON validates against JSON schema in evidence parser.

- **Action:** Before merging a sub-task branch, verify that all quality gates pass and evidence chain is complete.
  - **Quality Gate Run:** Execute `npm run check` on sub-task branch. If any check fails, block merge and require remediation.
  - **Evidence Chain Validation:** Parse all commits on sub-task branch; verify each has structured evidence in body. Count evidenced commits; require >= 1 evidence commit per distinct code/content change.
  - **Regression Detection:** Compare branch HEAD against parent HEAD using `git diff parent_branch...HEAD`. Flag any unintended changes or deletions; require explicit approval in evidence message if regression is intentional.
  - **Acceptance Criteria:** All checks pass; no regression warnings; evidence-count >= 1; merge proceeds to parent branch.

### Sub-Task Merging & Cleanup

- **Action:** Merge completed sub-task branches back to parent task branch with conflict resolution guided by evidence chains.
  - **Merge Command:** From parent branch, run `git merge --no-ff {subtask_branch}` to preserve merge commit and evidence trail.
  - **Conflict Resolution:** If conflicts arise, use evidence hashes from competing commits to determine priority. Evidence with more recent `confirmation` timestamp or stronger verification method takes precedence. Update merge commit with reconciliation evidence.
  - **Recursive Merging:** If sub-task branches have sub-sub-task dependencies, ensure dependency-ordered merging (leaves before parents) to minimize re-merges.
  - **Acceptance Criteria:** Merge commit created; no unresolved conflicts; merge commit includes evidence of conflict resolution strategy.

- **Action:** After all sub-tasks merge to the parent task branch, merge the parent into root development branch to seal the cognitive memory structure.
  - **Final Root Merge:** From root branch (e.g., `main`), run `git merge --no-ff {parent_task_branch}` with final evidence commit summarizing all sub-task completion.
  - **Final Evidence Commit:** Commit body must list all sub-task branches merged and final status. Example:

    ```json
    {
      "evidence": {
        "what": "Merged 3 sub-tasks: L3 design, L4 actions, L4 prevention into parent P1-9-polish task",
        "why": "All sub-tasks complete per evidence chain; P1-9 now has deterministic branching strategy and checkpoint schema",
        "confirmation": "All sub-task branches passed npm run check; evidence chains validated; no regression detected"
      }
    }
    ```

  - **Acceptance Criteria:** Root merge succeeds; final evidence commit is present; all prior sub-task commits are reachable via root branch history.

- **Action:** Clean up merged sub-task branches and worktrees to prevent stale accumulation (P3-1 entropy control).
  - **Worktree Cleanup:** After merge succeeds, run `git worktree remove .claude/worktrees/{task_id}-{checkpoint_n}` to delete worktree directory and `.git/worktrees/` registry entry.
  - **Branch Cleanup:** Run `git branch -d {subtask_branch}` to delete local branch (only after merge succeeds).
  - **Remote Cleanup:** If branches were pushed, run `git push origin --delete {subtask_branch}` to clean remote.
  - **Checkpoint Archival:** Move completed checkpoint from `.harness/branch-{branch_id}-checkpoint.json` to `.harness/archived-checkpoints/` directory for audit trail.
  - **Acceptance Criteria:** Worktree directory deleted; branch no longer appears in `git branch -a`; checkpoint moved to archive.

### Tooling & Automation

- **Tool:** `/cognitive-branch` workflow — enforces three-phase cycle (partition → execute → merge) with automated branching, checkpoint creation, and cleanup.
  - **Input:** Complex task description, estimated sub-task count, SAS vs MAS execution mode.
  - **Phase 1 Output:** Tracked branches created in `.git/worktrees/`, checkpoints stored in `.harness/branch-*-checkpoint.json`.
  - **Phase 2 Output:** Evidence commits on each sub-task branch.
  - **Phase 3 Output:** Merged sub-tasks to parent, merged parent to root, cleaned worktrees and branches.
  - **Acceptance Criteria:** Workflow completes without human intervention for well-scoped sub-tasks; escalates to human if evidence validation fails or context budget exhausted.

- **Tool:** Git Worktrees — concurrent branch execution without workspace switching.
  - **Command:** `git worktree add .claude/worktrees/{id} {branch}`
  - **Benefit:** Multiple sub-tasks can progress in parallel (SAS: sequentially with reuse; MAS: truly parallel across agents).
  - **Cleanup:** `git worktree remove` after merge.

- **Tool:** Branch-name sensor (pre-commit hook or CI gate) — validates branch naming conventions.
  - **Implementation:** Pre-commit hook in `.git/hooks/pre-commit` or CI check in workflow file.
  - **Validation Rule:** Branch name must match regex `^(task|subtask)/[a-z0-9-]+(/checkpoint-[0-9])?$`.
  - **Rejection:** Commits on non-compliant branches are rejected with message: `"Branch '{name}' does not match cognitive-branch naming convention. Use task/[id]/checkpoint-n or subtask/[parent]/[feature]."`
  - **Acceptance Criteria:** All commits on cognitive branches pass validation; no non-compliant branches enter repository.

- **Tool:** Evidence Schema Validator — parses and validates evidence JSON in commit bodies.
  - **Implementation:** Node.js script in `scripts/validate-evidence.js` or equivalent.
  - **Schema:** Validate JSON in commit body against required fields: `evidence.what`, `evidence.why`, `evidence.confirmation`.
  - **Integration:** Run as part of `npm run check` or as merge-blocker.
  - **Acceptance Criteria:** All evidence commits validate; non-conforming commits are flagged and require remediation before merge.

## L4: Prevention

### Prevent Monolithic Task Failures

**Rule:** You must prevent agents from attempting large, complex tasks in a single unbroken stream on `main` branch.

**Enforcement Mechanism:** `/cognitive-branch` workflow is **mandatory** for any task requiring more than 3 sequential steps or touching > 5 files. Agents must invoke the workflow before starting work; task-definition comments in plans must cite the workflow invocation.

**Consequence of Violation:** A monolithic branch fails midway, causing loss of incremental progress and forcing full restart. Context window exhaustion becomes likely because all intermediate state is lost. Evidence chains are non-existent, preventing resume/recovery.

**Mechanical Enforcement:**
- AGENTS.md explicitly states: "use `/cognitive-branch` workflow for complex multi-step objectives" (per Task Execution & Cognitive Memory section).
- When task-state utility is used (via `npm run task-state`), the entry must reference the cognitive-branch workflow ID if task involves > 3 steps.
- Task-state validator (`scripts/task-state-validator.js`) flags tasks with step_count > 3 and no `cognitive_branch_workflow_id` recorded.

### Prevent Context Loss on Branch Switch

**Rule:** Before creating a new sub-task branch, the cognitive-branch workflow must verify that the checkpoint contains the full prior-state context.

**Verification Mechanism:**
1. **Hash Computation:** Recompute SHA-256 hash of all prior findings, commits, and context from parent branch back to root.
2. **Hash Comparison:** Compare computed hash against `context_hash` field in parent checkpoint. Must match exactly.
3. **Token Count Validation:** Verify `prior_findings_tokens + current_session_tokens <= token_budget_total`. No branch creation if budget exhausted.
4. **Context Completeness Check:** Verify checkpoint JSON contains all required fields (see checkpoint schema in L3).
5. **Abort on Mismatch:** If any verification fails, halt branch creation and emit diagnostic:

   ```json
   {
     "error": "CONTEXT_LOSS_DETECTED",
     "detail": "Context hash mismatch: expected abc123, computed def456",
     "recommendation": "Possible context corruption or unexpected state change. Review parent-branch evidence and manual rebuild checkpoint if needed.",
     "escalate_to": "human"
   }
   ```

**Mechanical Enforcement:**
- Pre-branch-creation hook in `/cognitive-branch` workflow validates checkpoint before `git worktree add`.
- If validation fails, workflow stops with diagnostic (no rollback needed; branch creation was prevented).
- Escalation event appended to `.harness/escalation-events.jsonl` for human review.

### Prevent Unnamed or Misnamed Branches

**Rule:** All branches created by cognitive-branch workflow must follow naming convention: `task/{task_id}/{checkpoint_n}` or `subtask/{parent_id}/{feature}`.

**Enforcement Mechanism:** Branch-name sensor (pre-commit hook) validates branch name on every commit:

```bash
# Pre-commit hook logic
BRANCH_NAME=$(git rev-parse --abbrev-ref HEAD)
if ! [[ $BRANCH_NAME =~ ^(task|subtask)/[a-z0-9-]+(/checkpoint-[0-9]+)?$ ]]; then
  echo "ERROR: Branch '$BRANCH_NAME' violates cognitive-branch naming convention."
  echo "Use: task/{task_id}/checkpoint-{n} or subtask/{parent}/{feature}"
  exit 1
fi
```

**Consequence of Violation:** Non-compliant branch names break cognitive addressability:
- Downstream agents cannot parse task_id or checkpoint_n from branch name.
- Automated task-resumption logic fails because it cannot identify prior-state.
- Branch cleanup automation skips unmapped branches, causing stale-branch accumulation.

**Mechanical Enforcement:**
- `.git/hooks/pre-commit` contains above validation script (or equivalent in Node.js).
- CI gate (GitHub Actions / similar) also validates branch names for safety.
- Non-compliant commit is rejected with clear remediation message.
- Branch must be renamed (or commits rebased to new branch) before merge.

### Prevent Narrative Cognitive History

**Rule:** All approval-of-evidence records must be JSON-structured, not narrative-only, to enable machine parsing and automated task-resumption.

**Enforcement Mechanism:** Evidence validator (`scripts/validate-evidence.js` or integrated into `npm run check`) parses commit bodies and validates JSON structure:

```json
{
  "evidence": {
    "what": "required, string, min 10 chars",
    "why": "required, string, min 10 chars",
    "confirmation": "required, string, min 10 chars"
  }
}
```

**Consequence of Violation:** Without JSON structure, downstream tools cannot parse evidence:
- Context-reset recovery cannot determine whether prior phase completed or requires restart.
- MAS orchestrator cannot decide whether to merge, requeue, or reassign task.
- Audit automation cannot generate task-completion reports.

**Mechanical Enforcement:**
- Commit hook or merge-blocker parses commit body JSON and validates schema.
- If JSON parse fails, merge is blocked with message: `"Commit body does not contain valid evidence JSON. Required: {evidence: {what, why, confirmation}}"`
- Developers must update commit message and re-merge.
- `npm run check` includes evidence validation as binary pass/fail (not warning).

## L5: Gap Signals

- Agent processes multi-step complex objectives holistically in a monolithic branch
- No checkpointed cognitive history for distinct sub-tasks
- Sub-tasks are executed sequentially rather than concurrently when they could be parallelized
- Commit messages are sparse and lack structured evidentiary value
- Branch names do not follow a naming convention, making task context unrecoverable from branch alone
