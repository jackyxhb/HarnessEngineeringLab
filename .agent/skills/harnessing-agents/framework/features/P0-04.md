# P0-4. Ralph Loops

> **Chain:** [EP-4](../principles/EP-04.md) → Committed tasks must be completed

## L2: Targeted Enhancement

100% task completion rate regardless of context window exhaustion.

## L3: Design Decisions

Exit interception hooks; prompt reinjection with state summary; loop budgets to prevent infinite retries; integration with Planning for cross-window persistence.

### State Machine: Task Lifecycle

```json
┌─────────────┐
│   pending   │  Task created, awaiting execution start
└──────┬──────┘
       │ (npm run task-state -- start)
       ▼
┌─────────────┐
│   active    │  Task in progress; heartbeats emitted every checkpoint
└──────┬──────┘
       │ (all steps complete)
       ├─────────────────────────────┐
       │                             │
       │ (failure detected)          │ (success path)
       ▼                             │
┌─────────────────┐                 │
│  reinjected     │                 │
│  (loop budget)  │                 │
└────────┬────────┘                 │
         │ (reinjection_count < 3)  │
         │ (retry in fresh context) │
         └──────────────────┬───────┘
                            │
       ┌────────────────────┴──────────────────┐
       │                                       │
       │ (2+ consecutive failures              │ (all steps done)
       │  OR reinjection_count == 3)           │
       ▼                                       ▼
┌──────────────────┐                  ┌──────────────┐
│  escalated       │                  │  completed   │
│  (human review)  │                  │ (success)    │
└──────────────────┘                  └──────────────┘
```

### Task-State Structure Overview

The `.harness/task-state.json` file tracks task execution state across context windows. All state must conform to `.harness/task-state.schema.json`. Below is a concrete example:

```json
{
  "version": 1,
  "task_id": "task-polish-p004-20250416",
  "title": "Polish P0-4 Ralph Loops from needs polish to operational clarity",
  "plan_ref": "PLANS.md#P0-4-polish-20250416",
  "requirement_ids": ["REQ-P0-4-001", "REQ-P0-4-002"],
  "status": "active",
  "expected_steps": 4,
  "completed_steps": 2,
  "completed_step_labels": ["read-p004-file", "enhance-l3-design"],
  "current_step": "enhance-l4-actions",
  "state_summary": "Processed L3 with state machine; L4 Actions and Prevention in progress",
  "reinjections_used": 0,
  "max_reinjections": 3,
  "consecutive_failures": 0,
  "last_failure": null,
  "reinjection_summary": null,
  "escalation_summary": null,
  "started_at": "2025-04-16T14:30:00Z",
  "updated_at": "2025-04-16T14:35:45Z",
  "last_heartbeat_at": "2025-04-16T14:35:45Z"
}
```

**Key Fields:**
- `status`: One of `active`, `blocked`, `completed`, `escalated`.
- `expected_steps` / `completed_steps`: Numeric counters for task progress tracking.
- `completed_step_labels`: Human-readable list of finished substeps (used for reinjection context).
- `reinjections_used`: Incremented on each reinjection; triggers escalation at >= 2.
- `consecutive_failures`: Tracks back-to-back failures on the same step; used for escalation detection.
- `last_failure`: Capture timestamp, step name, and error message on failure.
- `started_at` / `updated_at` / `last_heartbeat_at`: ISO 8601 timestamps for timing analysis.

## L4: Concrete Actions & Tools

### Exit Interception

- **Action:** Implement exit interception hooks that detect premature completion.
  - **Tool:** `node scripts/exit-interceptor.js` — Runs automatically or via `npm run exit-check` after task completion to detect incomplete steps against `.harness/task-state.json`.
  - **Tool:** `.harness/task-state.json` schema-driven state file per AGENTS.md; must conform to `.harness/task-state.schema.json`.
  - **Timing:** Exit interceptor must detect premature exits within **1 second of task exit** before the execution context closes. For long-running tasks, this timing is enforced by heartbeat checks: if `last_heartbeat_at` is older than 30 minutes, the task is considered stale and triggers escalation.
  - **Exit Detection Logic:** Compare `completed_steps` against `expected_steps`; if unequal and `status` is not `completed` or `escalated`, trigger reinjection event.
  - **Acceptance Criteria:** Exit interceptor detects any task with status != `completed` within detection latency < 1 second; triggers reinjection if steps remain unfinished.

### State Persistence & Reinjection

- **Action:** Build prompt reinjection with state summary into fresh context windows.
  - **State Persistence Format:** `.harness/task-state.json` persists across reinjections with fields per `.harness/task-state.schema.json`:
    - `task_id`: Unique identifier for deduplication across reinjections.
    - `status`: Enum (active, blocked, completed, escalated).
    - `expected_steps` / `completed_steps`: Numeric progress counters.
    - `completed_step_labels`: Array of human-readable step names (e.g., ["read-source-file", "analyze-structure"]).
    - `reinjections_used`: Counter incremented on each reinjection.
    - `consecutive_failures`: Counter for back-to-back failures on the same step.
    - `last_heartbeat_at`: ISO 8601 timestamp; used to detect stale tasks (> 30 min old).
  - **Reinjection Compression:**
    - Reinjection payload must compress task state to **< 500 tokens or < 10% of original context**, whichever is smaller.
    - Compression strategy: drop verbose error traces, keep only step names and final error message; omit completed step details.
    - Example compressed summary: "Resume task-12345 (4/6 steps done). Completed: [step-1, step-2, step-3, step-4]. Pending: [step-5, step-6]. Last error: 'File not found on retry; check path.'"

  - **Reinjection Injection Point:** Fresh prompt receives reinjected state prepended **before** the original task objective, formatted as:

    ```text
    === TASK RESUMPTION CONTEXT ===
    Task ID: {task_id}
    Status: {status} (Reinjection #{reinjections_used})
    Progress: {completed_steps}/{expected_steps} steps
    Completed: {completed_step_labels}
    Current Step: {current_step}
    Last Failure: {last_failure.message}

    === RESUME OBJECTIVE ===
    {original_task_objective}
    ```
  
  - **Acceptance Criteria:** Reinjected prompt includes task context, completed steps list, current step, and pending work; agent resumes from exact failure point without repeating completed work. Reinjection payload size verified < 500 tokens via token counter.

### Loop Budget Enforcement

- **Action:** Add loop budgets (max reinjections) to prevent infinite retries.
  - **Loop Budget Rule (from AGENTS.md):** "Maximum 3 reinjections per task to prevent infinite retries. Escalate to human review after 2 failed reinjections."
  - **Hard Limit:** `reinjections_used` **must never exceed 3**. Once `reinjections_used >= 3`, task **automatically transitions to `escalated` status** and human review is required.
  - **Escalation Trigger:** Escalation event emitted to `.harness/escalation-events.jsonl` when **either**:
    - Condition A: `reinjections_used >= 2` **AND** `consecutive_failures >= 1` (2+ reinjections + current failure)
    - Condition B: `reinjections_used >= 3` (hard limit reached)
  
  - **State Tracking:** `.harness/task-state.json` field `reinjections_used` increments immediately upon reinjection detection; checked before allowing reinjection to proceed.
  - **Acceptance Criteria:** Task reinjections never exceed 3; after 2+ reinjections with failure, escalation event is automatically created with structured diagnostic (task_id, title, attempted steps, why it failed, proposed alternative action).

## L4: Prevention

### Prevent Infinite Loops (Reinjection Cycles)

**Problem:** Without loop budgets, reinjection can cycle indefinitely if the same failure recurs across reinjections.

**Concrete Detection Mechanism:**
- **N-Consecutive Reinjections:** Detect when `reinjections_used` increments N times on the same `task_id` within a time window.
  - Threshold: **N = 3 reinjections** (hard limit per AGENTS.md).
  - Time window: From task start (`started_at`) to current time; no rolling-window reset.
  - Detection: Checked in exit-interceptor before emitting reinjection event.
  
- **Entropy-Based Detection:** If the same `current_step` is retried after reinjection and `consecutive_failures` increments, it signals non-progress.
  - Threshold: **consecutive_failures >= 3** on the same step.
  - Detection: Checked after each step failure; if exceeded, escalate immediately even if `reinjections_used < 3`.
  
- **Time-Based Bailout:** Detect tasks stalled in `active` status without heartbeat progress.
  - Threshold: **last_heartbeat_at older than 30 minutes** (from `.harness/escalation-rules.json`).
  - Detection: `npm run exit-check` scans all active tasks; if stale, transitions to `escalated`.

**Escalation Outcome:** Once any detection mechanism triggers, emit escalation event to `.harness/escalation-events.jsonl` with:

```json
{
  "timestamp": "2025-04-16T15:45:22Z",
  "task_id": "task-xyz",
  "reason": "reinjection_limit_exceeded",
  "reinjections_used": 3,
  "consecutive_failures": 2,
  "last_failure_message": "Same parsing error on retry; task blocked",
  "attempted_on_step": "analyze-structure",
  "proposed_alternative": "Switch to manual analysis and hand-off to human expert"
}
```

### Prevent Narrative Task State

- **`P0-4` Prevent Narrative Task State:** Task state snapshots and reinjection payloads must follow a machine-readable JSON schema to enable deterministic resumption and audit across context windows.
- **Enforcement:** All `.harness/task-state.json` files must conform to `.harness/task-state.schema.json` (strict schema validation). Narrative-only state files (e.g., ad-hoc Markdown snapshots) are forbidden.
- **Verification:** `npm run check` validates all task-state files against schema; CI rejects non-conforming state. Consequence: prevents silent divergence of state format across reinjections.

## L5: Gap Signals

- Agent stops mid-task and declares "done" prematurely
- Long-horizon tasks consistently produce incomplete results
- Agent loses task context after restart
- Monolithic Tasks fail due to resource exhaustion or timeouts
- No record of current execution state for long-running processes
- Incomplete tasks cannot be resumed from the point of failure

## L5: Measurement

### Concrete Thresholds

**Reinjection Efficiency:**
- **Reinjection count per task:** < 3 (hard limit; >= 3 triggers escalation).
- **Successful completion on first attempt:** > 80% of all tasks (baseline; target 90%+).
- **Average reinjections per successful completion:** < 1.5 (if avg reinjections > 1.5, indicates repeated failure pattern).

**Detection & Escalation Timing:**
- **Exit detection latency:** < 1 second (exit-interceptor must identify incomplete tasks before context closes).
- **Escalation event emission latency:** < 1 second after escalation threshold is crossed (from detection to `.harness/escalation-events.jsonl` write).
- **Escalation time-to-human-visibility:** < 5 minutes (from escalation event write to user review; SAS: immediate; MAS: routing delay acceptable).

**Task Completion & Reliability:**
- **Premature exit rate:** 0% (no task should exit with status != `completed` or `escalated`).
- **Long-horizon task completion rate:** > 95% (tasks with 5+ steps should complete successfully across reinjections).
- **Reinjection success rate (task completed after reinjection):** > 80% of reinjected tasks (if < 80%, indicates reinjection strategy ineffectiveness).
