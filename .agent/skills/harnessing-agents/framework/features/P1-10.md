# P1-10. Requirements Ledger

> **Chain:** [EP-11](../principles/EP-11.md) → If it's not in the repo, it doesn't exist

## L2: Targeted Enhancement

All requirements formally recorded before any planning or execution.

## L3: Design Decisions

Canonical REQUIREMENTS.md with structured entries (ID, title, narrative, acceptance criteria, status, source); pre-planning validation hooks; shared ledger with file locking for MAS.

## L4: Concrete Actions & Tools

- **Action:** Durable tracking of commitments and specifications; requirements-as-code; automated compliance verification; machine-readable ledger records; Machine-Readability First.
- **Action:** Each entry should capture: ID, title, narrative/scenario, acceptance criteria, status (recorded/planned/executed), and source (who/when).
- **Tool:** Canonical requirements file (e.g., `REQUIREMENTS.md`, `BACKLOG.md`) in the project root.
- **Tool:** Pre-planning validation hooks that check the ledger before plan/execute workflows proceed.

## L4: Prevention

- **`P1-10` Prevent Specification Drift:** You must prevent agents from modifying code without a corresponding entry in the requirements ledger. Every feature or refactor must be anchored to a documented requirement.
- **`P1-10` Prevent Narrative Requirements Ledgers:** Requirement definitions and compliance records must follow `.harness/requirement-entry.schema.json` and `.harness/compliance-record.schema.json` to enable automated verification.

## Enforcement Bindings

## L5: Gap Signals

- New features are implemented without clear specifications
- Requirement changes are lost in conversation history
- No way to verify if code meets all documented commitments
- Specification conflicts are not detected until late in development
- No canonical source of truth for user stories, acceptance criteria, or functional scenarios
- Planning proceeds without any reference to a documented backlog
