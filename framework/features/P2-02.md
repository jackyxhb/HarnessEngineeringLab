# P2-2. Dependency Enforcement

> **Chain:** [EP-15](../principles/EP-15.md) → Mechanical enforcement over advisory guidance

## L2: Targeted Enhancement

Architectural boundaries mechanically enforced, not just documented.

## L3: Design Decisions

### Boundary Model: Layered Architecture

Dependency enforcement uses a **layered boundary model** aligned with the 3-Pillar + 1-Foundation organizing framework:

```json
{
  "boundary_model": "layered",
  "layers": [
    {
      "layer_id": "foundation",
      "description": "Infrastructure execution layer (sandboxes, orchestration, verification)",
      "allowed_imports_from": [],
      "may_import": [],
      "circular_dependency_tolerance": "zero"
    },
    {
      "layer_id": "context-engineering",
      "description": "Pillar 1 (inform): context, memory, real-time data",
      "allowed_imports_from": ["foundation"],
      "may_import": ["foundation", "context-engineering"],
      "circular_dependency_tolerance": "zero"
    },
    {
      "layer_id": "constraints",
      "description": "Pillar 2 (constrain): mechanical enforcement, boundaries, access control",
      "allowed_imports_from": ["foundation", "context-engineering"],
      "may_import": ["foundation", "context-engineering", "constraints"],
      "circular_dependency_tolerance": "zero"
    },
    {
      "layer_id": "entropy-management",
      "description": "Pillar 3 (maintain): long-term codebase health, cleanup, consolidation",
      "allowed_imports_from": ["foundation", "context-engineering", "constraints"],
      "may_import": ["foundation", "context-engineering", "constraints", "entropy-management"],
      "circular_dependency_tolerance": "zero"
    }
  ],
  "enforcement_rule": "A module at layer N may import modules from layers 0..N only. Reverse imports (N→M where M > N) are forbidden."
}
```

### Allowed Paths vs Forbidden Paths

Dependency relationships are encoded as explicit white-list entries with status indicators:

```json
{
  "allowed_paths": [
    {
      "from": "framework/features/P1-*",
      "to": "framework/features/P0-*",
      "reason": "Pillar 1 may depend on Foundation",
      "status": "allowed"
    },
    {
      "from": "framework/features/P2-*",
      "to": ["framework/features/P0-*", "framework/features/P1-*"],
      "reason": "Pillar 2 may depend on Foundation and Pillar 1",
      "status": "allowed"
    }
  ],
  "forbidden_paths": [
    {
      "from": "framework/features/P0-*",
      "to": "framework/features/P1-*",
      "reason": "Foundation must not depend on Pillar 1 (would create circular risk)",
      "status": "forbidden"
    },
    {
      "from": ".agent/skills/*",
      "to": "framework/*",
      "reason": "Skills reference framework, not vice versa",
      "status": "forbidden"
    }
  ]
}
```

### Circular-Dependency Detection

All cyclic imports must be detected and reported automatically:

- **Detection Tool:** `madge --circular` (or `eslint-plugin-import` rule `no-cycle`) runs on every pre-commit and in CI.
- **Reporting:** JSON format with cycle paths, module names, and severity.
- **Tolerance:** Zero cycles allowed on main branch. Cycles in feature branches must be resolved before merge.
- **Escalation:** Violations auto-block commits and emit escalation events to `.harness/escalation-events.jsonl`.

## L4: Concrete Actions & Tools

### Action 1: Define Dependency White-List with Machine-Readable Schema

**Objective:** Declare allowed and forbidden dependency relationships in a structured format that both humans and CI can parse.

**Tool:** `.harness/dependency-white-list.json` (canonical live instance)  
**Schema:** `.harness/dependency-white-list.schema.json` (JSON Schema v7)

**Schema Example:**

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "Dependency White-List",
  "type": "object",
  "required": ["version", "boundaries", "allowed_paths", "forbidden_paths"],
  "properties": {
    "version": { "type": "string", "description": "Schema version (semver)" },
    "boundaries": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["module_id", "layer_assignment"],
        "properties": {
          "module_id": { "type": "string", "description": "Module/package ID" },
          "layer_assignment": {
            "type": "string",
            "enum": ["foundation", "context-engineering", "constraints", "entropy-management"],
            "description": "Architectural layer (P0-Foundation, P1-Pillar1, etc.)"
          },
          "allowed_dependencies": {
            "type": "array",
            "items": { "type": "string" },
            "description": "Modules this module may import"
          },
          "forbidden_dependencies": {
            "type": "array",
            "items": { "type": "string" },
            "description": "Modules to never import"
          },
          "description": { "type": "string" }
        }
      }
    },
    "allowed_paths": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["from", "to"],
        "properties": {
          "from": { "type": "string", "description": "Source module (glob pattern)" },
          "to": {
            "oneOf": [
              { "type": "string" },
              { "type": "array", "items": { "type": "string" } }
            ],
            "description": "Target module(s) (glob pattern)"
          },
          "reason": { "type": "string", "description": "Justification for this rule" },
          "exceptions": {
            "type": "array",
            "items": { "type": "string" },
            "description": "Specific file/module exceptions (requires escalation record)"
          }
        }
      }
    },
    "forbidden_paths": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["from", "to"],
        "properties": {
          "from": { "type": "string" },
          "to": {
            "oneOf": [
              { "type": "string" },
              { "type": "array", "items": { "type": "string" } }
            ]
          },
          "reason": { "type": "string", "description": "Why this dependency is forbidden" }
        }
      }
    }
  }
}
```

**Acceptance Criteria:**
- White-list file validates against schema on every commit (pre-commit hook).
- Schema defines at least 4 boundary layers and 20+ allowed/forbidden paths.
- Every documented architectural boundary in `AGENTS.md` and feature files maps to at least one rule.

### Action 2: Automated Circular-Dependency Detection

**Objective:** Detect and report all cyclic import relationships before they reach main branch.

**Tools:**
- `madge --circular` (primary detection engine)
- `eslint-plugin-import` rule `no-cycle` (secondary validation)
- Output: `.harness/dependency-violations-report.json`

**Report Format:**

```json
{
  "timestamp": "2026-04-16T10:30:00Z",
  "detection_tool": "madge",
  "violations": [
    {
      "violation_id": "circular-001",
      "type": "circular-dependency",
      "severity": "error",
      "modules": ["module-a", "module-b", "module-c"],
      "cycle_path": "module-a → module-b → module-c → module-a",
      "detected_files": [
        { "file": "src/a.js", "line": 3, "imported_module": "b" },
        { "file": "src/b.js", "line": 5, "imported_module": "c" },
        { "file": "src/c.js", "line": 7, "imported_module": "a" }
      ],
      "suggested_fix": "Remove import from module-c to module-a"
    },
    {
      "violation_id": "boundary-001",
      "type": "boundary-violation",
      "severity": "error",
      "from": "framework/features/P0-01.md",
      "to": "framework/features/P1-05.md",
      "reason": "Foundation (P0) must not import Pillar 1 (P1)",
      "detected_in": "line 45 of P0-01.md"
    }
  ],
  "summary": {
    "total_violations": 2,
    "circular_cycles": 1,
    "boundary_violations": 1,
    "detection_time_ms": 3200
  }
}
```

**Acceptance Criteria:**
- Detection completes in < 5 seconds on codebases with 1000+ files.
- Zero false negatives on test suite (100% recall on known cycles).
- False-positive rate ≤ 2% (acceptable transient issues resolved on second run).
- Report generated in JSON format, always available in CI logs.

### Action 3: Layered Enforcement (Pre-Commit + CI Gate)

**Objective:** Block violations at earliest point (development machine) and final gate (CI).

#### Pre-Commit Hook (Development Feedback)

**File:** `.husky/pre-commit`

**Actions:**
1. Run `madge --circular` on modified files only (fast path).
2. Run `scripts/validate-dependencies.js` to check white-list compliance.
3. Block commit if violations found.
4. Print error with fix suggestions and escalation path.

**Error Message Example:**

```text
❌ Dependency Validation Failed (P2-2)

Found 1 circular dependency:
  cycle-001: module-a → module-b → module-a
    at src/a.js:3 (imports b)
    at src/b.js:5 (imports a)
  Suggested fix: Remove line 3 from src/a.js or line 5 from src/b.js

Boundary violation:
  P0-01.md (Foundation) imports P1-05.md (Pillar 1)
    at line 45
  Reason: Foundation must not depend on Pillar 1

Bypass with: git commit --no-verify
Escalate: Create escalation record in .harness/escalation-events.jsonl
```

**Acceptance Criteria:**
- Hook runs in < 2 seconds on typical commits (< 10 changed files).
- Can be explicitly bypassed with `--no-verify`, but user sees warning.
- All violations block commit and require explicit bypass.

#### CI Gate (Merge Prevention)

**File:** `.github/workflows/dependency-check.yml` (or equivalent CI configuration)

**Actions:**
1. Run full `madge --circular` on entire codebase.
2. Run `scripts/validate-dependencies.js` with full white-list.
3. Report violations in standardized format.
4. Block PR merge if violations found.
5. Post comment on PR with violation details and remediation steps.
6. Emit escalation event if violations not resolved after 24 hours.

**Acceptance Criteria:**
- 100% of PRs with violations are blocked before merge (zero escapes to main).
- CI check result documented in GitHub PR checks UI.
- Violations reported as actionable comments (not generic failures).
- CI gate completes in < 15 seconds including full graph analysis.

### Action 4: Exception and Escalation Process

**Objective:** Allow legitimate exceptions while maintaining audit trail.

**Exception Flow:**
1. **Detection:** Pre-commit or CI detects violation.
2. **Assessment:** Developer or reviewer determines if exception is justified.
3. **Approval:** Escalation record created in `.harness/escalation-events.jsonl` with:
   - `escalation_id`: unique ID
   - `violation_id`: reference to specific violation
   - `type`: "dependency-exception"
   - `approved_by`: reviewer identity
   - `justification`: why this exception is acceptable
   - `duration`: temporary (deadline) or permanent
   - `timestamp`: when approved
4. **Exception Entry:** Add to `dependency-white-list.json` `exceptions` array with reference to escalation ID.
5. **Tracking:** `npm run observe` surfaces all active exceptions for periodic review.

**Escalation Event Schema:**

```json
{
  "escalation_id": "dep-exc-001",
  "timestamp": "2026-04-16T10:45:00Z",
  "agent_id": "agent-xyz",
  "violation_id": "circular-001",
  "type": "dependency-exception",
  "severity": "warning",
  "module_a": "src/legacy/auth",
  "module_b": "src/core/session",
  "violation_description": "Circular dependency: auth imports core/session, core/session imports auth",
  "justification": "Legacy auth module refactoring scheduled for Q2 2026. Cycle is isolated and does not affect new code paths.",
  "duration_type": "temporary",
  "expires_at": "2026-06-30T23:59:59Z",
  "approved_by": "reviewer-team",
  "approved_at": "2026-04-16T10:50:00Z",
  "remediation_plan": "Refactor auth module to use dependency injection pattern",
  "status": "approved"
}
```

**Acceptance Criteria:**
- All exceptions tracked in machine-readable format.
- Temporary exceptions have explicit expiration dates (max 90 days).
- Permanent exceptions documented with strong justification.
- `npm run observe` reports on exception health (expired, approaching deadline, etc.)

## L4: Prevention

- **`P2-2` Prevent Boundary Overreach:** You must prevent agents from importing cross-layer modules that bypass established architectural patterns (e.g., bypassing a repository abstraction to access a database directly). Enforcement mechanism: `madge` circular-dependency detection + `.harness/dependency-white-list.json` layer validation in `scripts/validate-dependencies.js`. Violation blocks commit via pre-commit hook and PR merge via CI gate. Consequence of bypass: circular dependencies corrupt the codebase, making refactoring impossible and breaking agent autonomy to safely modify code.

- **`P2-2` Prevent Narrative Architecture Maps:** Architectural boundary definitions and dependency white-lists must be stored in machine-readable JSON/YAML to allow CI enforcement, not as advisory prose in markdown documents. Enforcement mechanism: `he-lint.js` validates that every allowed/forbidden path rule in `AGENTS.md` maps to at least one entry in `.harness/dependency-white-list.json`. Narrative-only rules without corresponding `.harness/` entries will fail `npm run smoke` pre-commit. Consequence of violation: narrative rules are ignored by agents and CI validators, making boundaries merely aspirational rather than enforced.

- **`P2-2` Prevent Unstructured Violation Reports:** Dependency violations must be reported in machine-readable JSON format (`.harness/dependency-violations-report.json`), never as free-form log text. Enforcement mechanism: CI gate (`scripts/validate-dependencies.js`) produces only JSON output; human-readable summary is generated post-CI from JSON via GitHub Actions comment. Consequence of violation: agents cannot parse violations programmatically for automated remediation, and escalation routing fails.

## L5: Gap Signals

- Circular dependencies exist unchecked
- Agent imports modules that violate architectural boundaries
- Dependency conflicts not detected until runtime
- No automated validation of module boundary rules

## L5: Measurement

Operational definitions for P2-2 dependency enforcement success:

1. **Zero Circular Dependencies on Main:**
   - Metric: Count of cycles found by `madge --circular` on main branch HEAD.
   - Target: 0 cycles.
   - Failure mode: Any cycle found indicates PR escape (CI gate failed).
   - Escalation: Auto-escalate if > 0 cycles detected on main branch.

2. **Zero Boundary Violations on Main:**
   - Metric: Count of violations in `.harness/dependency-violations-report.json` (boundary-violation type) on main branch.
   - Target: 0 violations.
   - Failure mode: Indicates white-list enforcement failed or bypass occurred.
   - Escalation: Auto-escalate if > 0 violations detected on main branch.

3. **CI Gate Block Rate:**
   - Metric: (PRs blocked by dependency CI gate) / (total PRs attempted) × 100%.
   - Target: >= 98% (captures legitimate violations; < 2% false positive/escape rate).
   - Failure mode: < 98% indicates violations escaping CI gate or gate misconfigured.
   - Collection: GitHub Actions CI logs, counted weekly.

4. **Pre-Commit Hook Block Rate:**
   - Metric: (local commits blocked by pre-commit hook) / (total commit attempts) × 100%.
   - Target: >= 98% (catches violations before push attempt).
   - Failure mode: < 98% indicates developers frequently using `--no-verify` or hook disabled.
   - Collection: Pre-commit hook exit codes logged to `.harness/agent-logs.jsonl`, counted weekly.

5. **Detection Accuracy (Recall):**
   - Metric: Known cycle test cases / detected cycles × 100%.
   - Target: 100% recall (zero false negatives on test suite).
   - Failure mode: < 100% means `madge` missing real cycles.
   - Collection: `npm run observe` runs synthetic test suite with 50+ known cycles.

6. **Detection Accuracy (Precision):**
   - Metric: True violations / (reported violations) × 100%.
   - Target: >= 98% (false-positive rate ≤ 2%).
   - Failure mode: > 2% false positives causes alert fatigue and developer distrust.
   - Collection: Manual review of violation reports, counted monthly.

7. **Active Exceptions Tracking:**
   - Metric: Count of temporary exceptions with expiration_date < today.
   - Target: 0 expired exceptions.
   - Failure mode: Expired exceptions indicate process breakdown; escalate for remediation.
   - Collection: `npm run observe` checks `.harness/escalation-events.jsonl` for `type: dependency-exception` with `expires_at < now`.

8. **White-List Coverage:**
   - Metric: Documented boundaries in AGENTS.md / white-list rules × 100%.
   - Target: >= 95% (all major boundaries have corresponding rules).
   - Failure mode: < 95% indicates white-list is incomplete relative to architectural vision.
   - Collection: `he-lint.js` compares boundary mentions in prose to white-list entries.
