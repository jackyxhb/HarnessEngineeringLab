# Harness Engineering Architectural Principles

> _Canonical framework: `framework/Core Features for SAS.md` | Gap evaluation: `framework/HE Gap Evaluation Framework.md`_

A mature Harness Engineering (HE) environment relies on strict architectural boundaries across four key layers. Rather than trusting the agent's prompt to inherently produce good code, the environment structurally enforces it.

## Foundational Infrastructure (Execute)

The execution engine provides the safe environment and orchestration for autonomous agents:

- **Isolated Sandboxing:** Agents run in ephemeral, secure bash environments equipped with necessary tooling to prevent local contamination.
- **Filesystem & Git Integration:** The filesystem acts as durable storage and collaboration surface, where state is persisted and tracked via version control.
- **Self-Verification & Ralph Loops:** Agents must verify their own work via tests and logs before completing tasks. If they attempt to prematurely exit long-horizon tasks, "Ralph Loops" reinject the prompt to force completion.
- **Orchestration & Escalation:** Orchestration logic routes tasks between subagents and triggers human intervention policies only when the agent fails repeatedly.
- **Rippable Middleware:** Capabilities are built as modular middleware that can be phased out as underlying AI models natively improve over time.

## Pillar 1: Context Engineering (Inform)

Before an action occurs, the agent must seamlessly understand its environment without being overwhelmed ("Context Rot"):

- **Repository as Truth:** All project context, constraints, and architecture rules live directly in the codebase, eliminating reliance on human-only knowledge.
- **Progressive Disclosure & Compaction:** Tool logic is loaded only when assigned, and older memory is compressed to maintain a clean context window.
- **Observability as Dynamic Context:** Telemetry (logs, metrics, traces) is exposed to the agent in real time so it can evaluate system state autonomously during task execution.

## Pillar 2: Architectural Constraints (Constrain)

During execution, the solution space must be mechanically restricted to prevent dead ends:

- **Deterministic Linters:** Automated checks immediately flag and reject non-compliant code.
- **Dependency Enforcement:** Structural tests physically block the agent from violating architectural boundaries (e.g., UI importing directly from Repo).
- **LLM-Based Auditors:** Secondary AI agents review the primary agent's output to strictly verify compliance with project design philosophies and security bounds.

## Pillar 3: Entropy Management (Maintain)

After execution, the system must continuously guard against entropy generated by high-volume AI code output:

- **Scheduled Cleanups:** Dedicated background agents resolve circular dependencies and accumulating technical debt automatically.
- **Documentation Sync:** Dedicated agents actively audit and update project documentation to ensure it consistently matches the living codebase state.
- **Consolidation Loops:** Pipelines that aggregate changelogs, update architectural records, and track systematic issues across the repository to preserve global coherence.
